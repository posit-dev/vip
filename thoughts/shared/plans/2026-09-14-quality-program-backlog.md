## File-collision convention

`check_waves.py` groups every heading that starts `## Wave <digit>` into one bucket regardless of a trailing letter (`1a`/`1b` both become `1`), and it compares the **files** column as literal text across the whole bucket. Two rules follow, applied throughout this backlog:

1. When two PRs in the same wave-digit genuinely touch the same file and one depends on the other, the file is listed **only in the earlier row**. The later row omits it from `files` and its `depends on` cell says `<slug> (shares file)` or `<slug> (rebases on it for <file>)`.
2. Several wave-1 ruff-family PRs (see "Notes on wave 1 sequencing") could not be enumerated to exact file lists from the reviews' aggregate violation counts (`~2 sites`, `~40 sites`, etc.). Their `files` cell lists only `pyproject.toml` where the review named no other file, or is left blank when even `pyproject.toml` is already claimed upstream in the chain. The implementer confirms the real touched files by running the rule locally before opening the PR.

Every `pyproject.toml` edit in wave 1 forms one linear chain for exactly this reason: `lint-ble-enable-only` is the only row that lists `pyproject.toml`; every later wave-1 PR that also edits it says so in `depends on` instead.

## Notes on wave 1 sequencing

**Wave 1b starts after wave 1a merges.** Wave 1a is 18 small parallel PRs. Wave 1b's first PR (`lint-ble-enable-only`) adds a `# noqa: BLE001` suffix to 122 existing except lines across 32 files, some of which wave 1a edits on other lines (comments, docstrings). Sequencing 1b after 1a keeps every 1a PR conflict-free and makes 1.19 a trivial rebase. The `check_waves.py` script treats 1a and 1b as one bucket, so 1.19's `files` cell lists only `pyproject.toml` and its `depends on` cell carries the real file set by reference.

**Why a strict chain instead of one `lint-config` PR.** The design doc's lint-ratchet decision is "enforce in CI and fix in the same PR... nothing lands as a warning that can rot." A single `lint-config` PR that enables every approved family behind blanket `per-file-ignores`, with separate PRs later removing the ignores and fixing violations, would put every unfixed family's violations into exactly that rotting-warning state between the two PRs landing. The chosen alternative — one PR per family, each editing `pyproject.toml`'s `select` list and fixing its own violations in the same commit, sequenced so each rebases on the last — never has an enabled-but-unfixed family sitting in CI. The cost is a dependency chain (`lint-ble-enable-only` → `lint-small-families` → ... → `typing-strict-load-engine`, 15 rows after Ian's decision to bundle the eight ≤20-line families into `lint-small-families`) and the file-omission bookkeeping described above.

**Why bundle the eight smallest families instead of keeping one PR each.** Ian's call: `S101`, `C4`, `RET`, `PIE`, `PGH`, `ISC`, `TID`, `N`, and `B` each fix 20 lines or fewer (2 to 20, 82 combined) — small enough that a dedicated PR per family adds review overhead (a title, a body, a CI run, a rebase step) without a matching benefit, since none of them carries a design decision the way `S` (scope to `S101` only), `ARG` (scope to `src/vip`), or `PLC0415`/`PL` (defer the complexity family) do. `PTH` and `PERF` still get their own PR because each exceeds 20 lines on its own.

**Exact touched-file lists were not available for every family.** `typing-lint.md` gives violation counts (`~40 sites`, `~30 sites`, etc.) for `lint-pt`, `lint-sim`, and `lint-pl-subset` rather than exhaustive file lists, and `lint-d-formatting`'s autofix is explicitly repo-wide. Their `files` cells above are therefore sparse (often just noting the `pyproject.toml` rebase). The implementer confirms the real file set by running `uv run ruff check --select <FAMILY>` before opening each PR, and should re-check for an incidental overlap with the next PR in the chain if one surfaces (rebase, don't merge two families into one PR, to keep the one-PR-one-family invariant — `lint-small-families` is the one deliberate exception, already merged per Ian's decision above).

**`lint-d-vip-docstrings` and `lint-d-formatting` plausibly share files.** `lint-d-formatting`'s autofix touches existing docstrings repo-wide; `lint-d-vip-docstrings` adds new docstrings to the same 92 `src/vip/` sites. Some of those 92 files likely need both an autofix and a new docstring. `typing-lint.md` already flags this as a same-lines dependency; resolved here the same way as the pyproject.toml chain — sequential, `lint-d-vip-docstrings` rebases on `lint-d-formatting`.
