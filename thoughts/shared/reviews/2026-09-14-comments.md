# Review: comments

## Summary

VIP's comments are unusually careful for a test framework: most of the 123 grep hits for history-flavored language are not narration for its own sake but load-bearing rationale for a subtle bug that was fixed once and must not regress (a race, a timing edge, a proxy/httpx/Chromium disagreement). A prior pass (`issue #562`, referenced directly in `src/vip/plugin.py:356`) already targeted comment accuracy, and spot-checking the ten longest comment blocks in `plugin.py`, `cli.py`, and `auth.py` turned up no comment that is factually wrong about the code beneath it. The real problems are narrower: three session-scoped client fixtures in `fixtures.py` carry no docstring despite non-obvious caching and cookie-injection contracts, the two `install/plan.py` builder functions and `install/manifest.py`'s `load`/`save` have no docstring despite real validation and atomicity contracts, and a handful of comments genuinely are pure "it used to be X, now it's Y" narration that adds nothing a newcomer needs. The largest single risk is one 52-line comment block in `test_content_deploy.py` that embeds a date-stamped empirical claim ("as of 2026-07-29 this fired once") and explicitly warns the reader that its own claim will go stale — a warning worth taking seriously since nothing enforces the re-check it asks for.

## Findings

### `install/plan.py` builders and `install/manifest.py` load/save carry no docstring despite a real, non-obvious contract
Severity: high
Evidence: src/vip/install/plan.py:67 `def build_install_plan(`
Evidence: src/vip/install/plan.py:137 `def build_uninstall_plan(`
Evidence: src/vip/install/manifest.py:82 `def load(path: Path) -> Manifest | None:`
Evidence: src/vip/install/manifest.py:154 `def save(manifest: Manifest, path: Path) -> None:`
Why it matters to a newcomer: `build_install_plan` branches five ways by platform family and reconciles pending/legacy package names; `load` raises `ManifestError` on five distinct malformed-input shapes but returns `None` (not an error) for a missing or empty file; `save` writes through a `.tmp` file and `os.replace` for atomicity. None of that is visible from the signature, and AGENTS.md's own "Key source files" table (`Pure build_install_plan / build_uninstall_plan builders`, `.vip-install.json read/write (atomic)`) is currently the only place this contract is written down — outside the code it documents.
Proposed fix: Add a docstring to each of the four functions stating the return/raise contract (what `None` vs raising means for `load`, what "atomic" buys for `save`, what each platform branch of `build_install_plan` does) drawn from the AGENTS.md prose already describing them.
Proposed PR: docstrings-install (files: src/vip/install/plan.py, src/vip/install/manifest.py)

### `connect_client`, `workbench_client`, `pm_client` fixtures have inline comments but no docstring
Severity: medium
Evidence: src/vip/fixtures.py:103 `def connect_client(`
Evidence: src/vip/fixtures.py:166 `def workbench_client(`
Evidence: src/vip/fixtures.py:224 `def pm_client(vip_config: VIPConfig) -> Generator[PackageManagerClient | None]:`
Why it matters to a newcomer: each of these is 15-20 lines with scheme-resolution caching, session-cookie injection from a stashed Playwright auth session, and a `yield None` (not `return None`) contract for the unconfigured case — all covered by inline `#` comments but nowhere summarized as the fixture's contract. A newcomer skimming fixture signatures (the common way to learn what's available, per AGENTS.md's own "Fixtures available in product tests" table) gets no summary at the definition site.
Proposed fix: Add a one-to-two-sentence docstring to each of the three fixtures stating the `None`-when-unconfigured contract and the cookie-injection behavior; leave the existing inline comments for the *why* of each step.
Proposed PR: docstrings-fixtures (files: src/vip/fixtures.py)

### A handful of comments are pure history with no surviving rationale
Severity: low
Evidence: src/vip_tests/conftest.py:4 `step definitions used to live in this file. They moved to`
Evidence: src/vip_tests/cross_product/test_resources.py:3 `This module previously measured test-runner-local resources (disk usage,`
Evidence: src/vip/report_content.py:50 `Hoisted out of the per-card loop both templates used to have — each did`
Evidence: src/vip/cli.py:1336 `# Same helper plugin.py uses, so this finds the session a prior \`vip verify\``
Why it matters to a newcomer: these read as changelog entries bolted onto a docstring. The current behavior (what the module does now, why the helper is hoisted) is what matters; "used to measure test-runner-local resources" or "used to live in this file" tells a newcomer about a state that no longer exists and that they can never observe.
Proposed fix: Delete the "used to / previously" sentence in each; keep only the sentence describing current behavior. In `report_content.py:50`, keep "shared, since both pages need the identical substitution" and drop the loop-hoisting history.
Proposed PR: comments-strip-history (files: src/vip_tests/conftest.py, src/vip_tests/cross_product/test_resources.py, src/vip/report_content.py, src/vip/cli.py)

### Long "used to / previously" rationale comments in the three god-modules mix real invariants with change-history framing
Severity: medium
Evidence: src/vip/auth.py:73 `# _authenticate_workbench's post-Connect SSO wait. Workbench previously used`
Evidence: src/vip/auth.py:1341 `previously accepted it as done the moment \`\`networkidle\`\` fired (before`
Evidence: src/vip/auth.py:1512 `A timeout error used to hardcode "OIDC" even during a SAML run (see`
Evidence: src/vip/cli.py:1072 `the same _normalize_url every other entry point uses (it was previously`
Evidence: src/vip/cli.py:1476 `previously a scheme-less --connect-url was handed to ConnectClient`
Evidence: src/vip/fixtures.py:3 `These used to live in \`\`src/vip_tests/conftest.py\`\`. pytest scopes`
Evidence: src/vip/proxy.py:179 `than echoed verbatim -- the failure branch used to return the raw string, so`
Why it matters to a newcomer: unlike the previous finding, the rationale in these is genuinely load-bearing (why a shared 5-minute timeout exists, why URL normalization must be centralized, why the fixture module can't be a `conftest.py`). But the design doc's own comment policy ("one or two sentences on what and why... no change history") is violated by every one of these — each runs 4-8 sentences and leads with what the code used to do rather than what it does and why. This is a real, repeated style deviation across the framework's core modules, not isolated noise.
Proposed fix: Rewrite each to state the invariant/reason first and compress the "what changed" framing to a trailing clause or drop it, per the design doc's comment policy. Do this module-by-module so each PR stays reviewable against one file.
Proposed PR: comments-rationale-auth (files: src/vip/auth.py)
Proposed PR: comments-rationale-cli (files: src/vip/cli.py)
Proposed PR: comments-rationale-fixtures-proxy (files: src/vip/fixtures.py, src/vip/proxy.py, src/vip/plugin.py)

### A 52-line comment block embeds a date-stamped empirical claim that the comment itself says will go stale
Severity: medium
Evidence: src/vip_tests/connect/test_content_deploy.py:52 `# Filed as insurance, not a fix for chronic pain: as of 2026-07-29, this`
Evidence: src/vip_tests/connect/test_content_deploy.py:56 `# will go stale as more runs accumulate: re-run`
Why it matters to a newcomer: the comment (lines 28-79) is otherwise an excellent piece of reasoning about a narrow, deliberately-non-widened retry match, but it hands the reader a manual chore ("re-run `gh run list --workflow connect-smoke.yml`... before repeating either claim") with nothing that ever prompts that re-check. A newcomer six months from now has no signal that the "fired exactly once" claim is stale, and will either trust a rotted number or have to rediscover this warning by reading 52 lines of comment first.
Proposed fix: Keep the retry-match rationale (it is not history narration, it is the design), but move the empirical claim and its expiration warning out of the comment and into a linked, dated issue or a periodic-check TODO the team actually revisits, rather than leaving it as a comment nobody is prompted to re-verify. Out of scope for a wave-1 hygiene PR (it doesn't contradict the "no history narration" policy — it's not history at all), but should be raised with Ian for a wave-2/backlog item.
Proposed PR: comments-strip-history (no code change proposed here; flag for backlog discussion instead)

### Seven `from_dict` classmethods in `config.py` share one undocumented parsing contract
Severity: low
Evidence: src/vip/config.py:132 `def from_dict(cls, raw: dict) -> ConnectConfig:`
Evidence: src/vip/config.py:171 `def from_dict(cls, raw: dict) -> WorkbenchKubernetesConfig:`
Evidence: src/vip/config.py:195 `def from_dict(cls, raw: dict) -> WorkbenchExtensionsConfig:`
Evidence: src/vip/config.py:254 `def from_dict(cls, raw: dict) -> GitTestConfig:`
Evidence: src/vip/config.py:317 `def from_dict(cls, raw: dict) -> WorkbenchConfig:`
Evidence: src/vip/config.py:364 `def from_dict(cls, raw: dict) -> PackageManagerConfig:`
Evidence: src/vip/config.py:396 `def from_dict(cls, raw: dict) -> AuthConfig:`
Why it matters to a newcomer: someone adding a new `vip.toml` key needs to know whether an unrecognized key is ignored or rejected, and whether a missing key raises or defaults — that's config-schema behavior, not obvious from `from_dict`'s name, and it is repeated seven times with no single place stating the shared convention.
Proposed fix: One short docstring on the first `from_dict` (or a module-level note) stating the shared convention (tolerant of missing keys with dataclass defaults, silent on unknown keys), rather than seven near-duplicate docstrings.
Proposed PR: docstrings-config (files: src/vip/config.py)

## Not findings

- Ran the history-narration grep and manually classified all 123 hits; most are class (b) (history plus still-true rationale) rather than pure noise — see the two rationale findings above rather than treating the raw count as 123 problems.
- `selftests/install/test_plan.py`'s "no longer" and "legacy" hits are not history narration: "legacy" names a real Debian package-rename scheme still handled by current code (`libasound2` → `libasound2t64`), and "no longer installed" describes a test scenario, not a code change.
- `RSC-XSRF-legacy`, `SWITCH_TO_LEGACY`, and other "legacy" hits in `auth.py` and `workbench/pages/homepage.py` name real, currently-supported product modes (legacy cookie mode, legacy homepage), not deprecated code paths — not history narration despite matching the grep.
- Checked whether `used to` ever meant "in order to" rather than "formerly" (a real risk with this regex): confirmed at `auth.py:1842` (`_tls_listener_present` docstring) — false positive, not counted as a finding.
- Sampled the ten longest comment blocks in `plugin.py`, `cli.py`, and `auth.py` against the code they describe (URL-sync duplication across the `--interactive-auth`/`--headless-auth` branches in `plugin.py`, the XSRF cookie-name comment in `auth.py`, the Quarto-kernel-pinning comment in `cli.py`) and found none that misdescribe current behavior — a prior comment-accuracy pass (`issue #562`, cited at `plugin.py:356`) appears to have already caught this class of problem.
- `uv run ruff check --select D103,D102` flags 81 sites, but most (all seven `*_url` fixture siblings in `fixtures.py`, every `@task` method in `load_users.py`, `is_configured`/`total`/`passed`/`failed`/`skipped` accessors, the three `pytest_*` hook functions) have names that are the whole contract or are a well-known framework hook name; not counted as findings per the design doc's "non-obvious contract" bar.
- The 5+-consecutive-`#`-line scan over `src/vip/*.py` and `src/vip/**/*.py` (auth.py:1825, plugin.py:58, proxy.py:767, report_content.py:134/153, report_html.py:230, version.py:20/110, clients/workbench.py:24) found only comments explaining genuinely non-obvious invariants (cache-key composition, httpx/Chromium port-matching parity, session-ownership naming scheme, pre-release ordering policy) attached to module-level constants that cannot carry a docstring in Python — not flagged as findings; converting them to a helper function purely to get a docstring would be over-engineering for a one-constant module.
- `docs/`, `AGENTS.md` themselves are out of scope for this lens (docs-hygiene lens owns them) and were only read for context.
